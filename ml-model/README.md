# Nexora Smart Matching - ML Service

## What this is
A standalone Python service (FastAPI) that scores how compatible a farmer
listing is with a buyer demand, and returns a ranked list. Your Node backend
calls this service over HTTP - it does not run inside Node.

## Files
- `matching_core.py` — feature engineering + heuristic labeling logic.
  Shared by training and serving so they never drift apart.
- `train.py` — offline training script. Run this yourself whenever you get
  new/updated data. Produces the `models/` folder.
- `app.py` — the live API (FastAPI). Loads the trained model once at startup.
- `listings.csv`, `demand.csv` — the ML service's own copy of the data, used
  for candidate retrieval. Replace these with your real exported data before
  training, and keep them in sync with MongoDB if the data changes.
- `models/` — generated by `train.py`: `model.pkl`, `baseline_ridge.pkl`,
  `feature_columns.json`. These are the only things that need to exist for
  `app.py` to run - you do not need to retrain every time you start the app.

## Setup (local, VS Code)

```bash
cd ml-service
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt

# Train once (takes ~10-20 seconds on a laptop):
python3 train.py

# Run the API:
uvicorn app:app --reload --port 8000
```

Then check it's alive:
```
GET http://localhost:8000/health
-> {"status": "ok"}
```

## Calling it from Node

Two endpoints, matching the two directions of Smart Matching:

### Buyer searching for farmer listings
```
POST http://localhost:8000/match/buyer-to-farmer
Content-Type: application/json

{
  "crop": "Cotton",
  "variety": "Not Specified",
  "required_quantity_tons": 15,
  "maximum_price_per_quintal": 8800,
  "required_by_date": "2026-08-01",
  "cluster": "Vidarbha",
  "district": "Chandrapur",
  "taluka": "Warora",
  "village": "Abamakta",
  "top_k": 20
}
```
Returns the top 20 (or fewer, if fewer candidates exist) ranked listings with
a `compatibility_score` (0-100) attached to each.

### Farmer looking for buyer demand
```
POST http://localhost:8000/match/farmer-to-buyer
Content-Type: application/json

{
  "crop": "Soybean",
  "variety": "JS 335",
  "quantity_tonnes": 12,
  "price_per_quintal": 5800,
  "harvest_date": "2026-04-10",
  "cluster": "Vidarbha",
  "district": "Amravati",
  "taluka": "Chikhaldara",
  "village": "Churni",
  "top_k": 20
}
```

### Example Node/Express controller
```js
// controllers/matchingController.js
const axios = require('axios');
const ML_SERVICE_URL = process.env.ML_SERVICE_URL; // e.g. http://localhost:8000

exports.matchListingsForBuyer = async (req, res) => {
  try {
    const { data } = await axios.post(
      `${ML_SERVICE_URL}/match/buyer-to-farmer`,
      req.body
    );
    res.json(data);
  } catch (err) {
    console.error('ML service error:', err.message);
    res.status(502).json({ error: 'Matching service unavailable' });
  }
};

exports.matchDemandForFarmer = async (req, res) => {
  try {
    const { data } = await axios.post(
      `${ML_SERVICE_URL}/match/farmer-to-buyer`,
      req.body
    );
    res.json(data);
  } catch (err) {
    console.error('ML service error:', err.message);
    res.status(502).json({ error: 'Matching service unavailable' });
  }
};
```
Add `ML_SERVICE_URL=http://localhost:8000` to your `.env` locally, and to
Render's environment variables once deployed (it'll be the Render URL of
this service instead).

## Known limitations (be upfront about these in your demo)
- No real transaction-linked "this pair actually worked" data exists yet, so
  the model is trained against a defined compatibility heuristic (crop,
  price fit, geography, quantity, variety, timing) rather than real outcomes.
  It's a genuine, evaluated ML model - just honest about what it's modeling.
- This service holds its own in-memory copy of listings/demand data, loaded
  at startup. If new listings/demands are added to MongoDB while the service
  is running, this copy won't see them until the service restarts/retrains.
  Fine for a demo; production would query MongoDB directly or refresh
  periodically.
- Evaluated with Precision@10 ≈ 0.97 and R² ≈ 0.91 against the heuristic on
  held-out demand records (see train.py output) - this measures how well the
  model reconstructs the defined compatibility notion, not real-world
  transaction success.
